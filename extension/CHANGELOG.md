## [0.13.0] - 2026-08-12

### Added

- **Describe a query in plain English and the SOQL lands in the editor — never in the org.** The runner's toolbar gains **Generate query**, which opens a prompt panel above the editor: type what you want, optionally name the objects, press Generate. The answer is written into the query editor and the status line says *review it, then Run*. Nothing runs. That is not a policy the button follows, it is the shape of the code: `generateSoql()` in `features/soql-nl-generate.ts` is the only orchestrator, its dependency interface contains a describe, a global-describe list, a prompt gate and the bridge call, and **nothing that can execute SOQL** — so there is no path from "the model answered" to "the org ran it" for a future change to take by accident. `test/soql-nl-generate.test.ts` proxies that dependency object and pins the exact four property names the function ever reads, and the wiring test drives a whole generation and asserts the Salesforce client recorded zero query calls — then presses **Run** and asserts it recorded one, so the first assertion is not vacuous. A generated string that fails the local SOQL checks (the same rules as the CLI's `sfdt soql validate`) is reported rather than pasted, because an unusable answer must not overwrite the draft you already had.
- **The prompt carries schema, and there is a gate that stops it carrying anything else.** What goes on the wire is your description plus a Markdown field table per object, in the identical format the **Export for Prompt** feature copies to your clipboard — the same `buildSchemaMarkdown()`, so the two cannot drift into two dialects. Fields reach it through `schemaFieldsForPrompt()`, an **allowlist** of five metadata properties (`name`, `label`, `type`, `nillable`, `inlineHelpText`) that rebuilds each entry property by property, so a describe payload polluted with anything at all contributes nothing; and the assembler takes a request string and schemas, with no records parameter and no client it could fetch one with. On top of that structural guarantee sits a backstop the orchestrator must clear before it may send: `recordValueLeak()` scans the assembled prompt — minus your own words, which are yours — for any value from the result set currently on screen, and a hit ends the generation with nothing sent. Objects are inferred from your wording against the org's own sObject list (never invented) or typed in explicitly; the field table is capped at 150 fields per object and says so in the prompt rather than truncating silently.
- **Zero LLM endpoints in the extension, enforced by a sweep.** Generation goes through the bridge plumbing `features/ai-assistant.ts` already used — `createBridgeClient(...).call({ kind: 'ai', prompt })` — so the provider, the API key, the redaction pass and the anti-injection preamble all stay on the CLI side of `sfdt ui`, and the extension gains **no new manifest permission and no new host**. `test/no-llm-endpoints.test.ts` scans every shipped `.ts` file for a model-provider hostname or a key-shaped credential, forbids `fetch`/`XMLHttpRequest`/`WebSocket` inside either AI feature, and asserts the manifest's `host_permissions` still lists only Salesforce and localhost. Per golden principle #12 it excludes itself, by name and with the reason.
- **Off by default, and it tells you how to switch the other half on.** `soql-nl-generate` is its own registry feature with `enabledByDefault: false` — the second feature in the extension to ship off, and for a different reason than the first: it does nothing destructive, but it moves org schema *out of the browser*, which is a decision that belongs to you. Until you tick its row on the options page (badged *Off by default* and *Needs sfdt bridge*) neither the toolbar button nor the panel is **built** — absent, not hidden. When it is on but the other end is not ready, the panel keeps the bridge's own diagnosis (offline, unpaired token, or the CLI's `"features.ai": false`) and appends the steps under it as separate nodes through `renderSfError`'s guidance channel: run `sfdt ui`, pair on the options page, set `"features.ai": true` in `.sfdt/config.json`. A plain provider failure — a rate limit — deliberately gets **no** setup advice, because telling someone to configure something they already configured is worse than saying nothing. Generation is SOQL-only: switching the runner to SOSL closes the panel and disables the trigger with a title that says why.
- **Bulk delete from a SOQL result set — off by default, and built as a set of guard rails rather than a delete button.** The runner's result toolbar (and each SOSL object group's copy of it) gains **Delete N rows** when the rows carry an `Id`, and clicking it runs a fixed sequence: the affected rows are **serialised to a backup CSV and handed to the browser first**, then a modal asks you to type `DELETE 12 Account` exactly, and only then does anything go to the org. The ordering is the feature. In `features/soql-bulk-delete.ts` there is exactly ONE exported function that can reach a delete, it plans the rows itself rather than trusting a caller's plan, and both gates are `=== true` checks — a backup callback that returns `false`, returns `undefined`, or throws ends the operation with nothing deleted and the dialog never shown, and a confirm that throws counts as a refusal. Escape cancels; it can never confirm. The rows go out through the same `recordsToCsv` the **Export CSV** action uses and the same `lib/download.ts` every other export uses, so the backup quotes commas and quotes exactly the way the export you already trust does — a second serialiser would have been a second set of quoting bugs, discovered at the worst possible moment. Deletes run in waves of 25 rather than one unbounded `Promise.all`, because a 2,000-row result set fired at once either trips the org's concurrency limit or hangs silently; each wave reports progress, and a **Cancel** control (plus closing the runner, or running a new query) stops the next wave. Failures do not abort the run: every row that did not delete is listed by Id with the reason, classified by `sfApiErrorKind`'s discriminant rather than by matching error prose, and a **timed-out** row is called out separately as *may still have committed* — the one failure whose outcome is genuinely unknown, and the one where a blind retry deletes something twice. Rows the org confirms gone are removed from the table; rows that failed — including the timed-out ones — stay, because they are what you re-check.
- **The backup gate checks the payload, and the dialog says what it cannot prove.** "The download call did not throw" is a much weaker fact than it reads as: it is equally true of a backup containing nothing. The gate now verifies that the generated CSV actually contains **every Id in the delete plan**, and that the browser accepted the blob — either failing deletes nothing. What it still cannot do is confirm the file reached your disk; that needs the `downloads` permission, which the extension deliberately does not have. So the confirm dialog **names the file** (`sfdt-delete-backup-Account-2026-08-05.csv`) and asks you to check your downloads, rather than asserting a guarantee that is not the extension's to make. It also states that the backup holds only the columns the query selected — a partial backup is a partial restore, and finding that out at restore time is too late.
- **The first feature that ships switched OFF.** `soql-bulk-delete` is its own registry feature with `enabledByDefault: false`, so it has a kill-switch id and its own row (badged *Off by default*) on the options page, and the SOQL runner never builds the control until you tick it — the button is *absent*, not hidden, since a hidden destructive button is one style write away from being clickable. Its own id rather than a `soql-runner` sub-flag because a kill switch has to be able to take the destructive half away without taking the query runner away; and deliberately *not* a single shared "record delete" switch spanning the forthcoming single-record delete, because deleting the one record you are looking at and deleting every row a query returned are different sizes of mistake. This is what C-FIX-2 made `enabledByDefault` authoritative at runtime *for*: `test/feature-manifests.test.ts`'s "no shipped feature ships off" invariant is now an explicit reviewed allowlist, and asserts the runtime resolves this id to disabled for a user with no stored preferences. No new manifest permission — a record `DELETE` rides the worker-proxied `sfApiFetch` route every other write already uses.
- **A caller cannot silently break the confirm dialog's focus restore any more.** `test/confirm-dialog-trigger-contract.test.ts` is a source sweep, in the shape of the error-panel one: it flags a `.disabled = true` that lexically precedes a `confirmDialog(…)` call reached from the same function body, so the *next* caller writing that shape hits a red test instead of a code review. The previous release said the shared layer's tests delivered that; they did not — they pin the DIALOG's behaviour and cannot see a violating caller, and `features/debug-log-viewer.ts` was the live proof, carrying the banned shape with the whole suite green. The rule asks the TypeScript parser rather than matching braces (scope is the question, and a hand-rolled scanner is what has holed the sibling guard three times), and it reuses that guard's fail-closed masker so an unterminated literal makes it refuse rather than go quiet. Order and nesting are both load-bearing: disabling *after* the dialog answers is the correct fix and is not flagged, two sibling callbacks are not flagged in either order, and a disable in the enclosing body is flagged when that body goes on to `await` something — a control-flow fact, deliberately not "the call sits inside the await's text", which a one-line `const` hoist walks straight out of while the callback still runs. It carries **no exclusions** — the dialog's own doc comment writes the banned shape verbatim and is prose, not code, which is exactly what the mask and the parser are there to know.
- **A contract sweep (`test/sf-error-panel-contract.test.ts`) that fails the next hand-roll.** The two guards that came out of the last release pin what a correct error panel *looks* like; a brand-new hand-rolled panel that happens to satisfy both still passes them, which is exactly how sixteen of them accumulated. This one pins the code *path*, in three rules: `.sfdt-console` + `.sfdt-error` on one element is the Salesforce error block and only `ui/panels.ts` may build it; no `.sfdt-console` element may be handed a caught error's text directly, which is the styling-free shape above; and nothing may pass an already-stringified error to the shared renderer. That third rule guards the hole the fix itself opened: the renderer takes `unknown` so a caller can pass its own prose, `unknown` accepts a string, and `err.message` at a call site therefore compiles clean while silently flattening the structure the renderer exists to keep apart. No type distinguishes "our sentence" from "an error someone already stringified", so a check does. The first rule is the class **pair**, not `.sfdt-error` alone — that is also the red `.sfdt-pill`, which several features legitimately apply to a status chip — and it accumulates classes **per element rather than per statement**, because a version that read one application at a time was blind to `add('sfdt-console')` followed by `add('sfdt-error')`, which is the shape an author writing a reused pane produces first. Splitting across statements, `setAttribute('class', …)`, `className +=`, template interpolation, a spread of a constant array, `let`/`var` accumulators, `classList.toggle` and `Object.assign` are each covered by a case; element access other than through a plain identifier, aliasing, and runtime-computed class names are consciously left open and said so in a comment. The second and third rules no longer carry an identifier alternation each: an identifier bound by `catch` holds an error whatever it is spelled, and so does one bound to an expression that flattens one, so both rules ask `test/error-source-scan.ts` — one shared definition, shared with `test/error-render-newlines.test.ts` as well. Two alternations that disagreed about what an error is called was the defect generator; the spelling list survives only as the fallback for a function *parameter*, which is bound at the call site and which no in-file scan can follow. Per golden principle #12 the sweep excludes the artifacts that define it: the helper, and this file. The **stylesheet is not excluded** — it declares the class names inside a CSS template string and no rule reads CSS, so it tripped nothing and an exclusion that excludes nothing is a hole, not an exclusion. A test now proves that property for every remaining entry rather than merely checking the file still names the classes. The sweep carried a `LITERAL_ONLY` suppressor for one round, meant to skip fixed copy, whose character class excluded quote characters but not `$` or `{` — so an interpolating template literal read as fixed copy, and a console pane assigned a template that interpolates `err.message` was suppressed on both guards at once. Measured against the whole tree it suppressed *nothing*: short-circuited, the suite stayed green. It is deleted. `dynamicParts()` — the expression with the text inside its string literals blanked out, so a template keeps its `${…}` holes and loses its prose — is the same intent expressed so it cannot fail that way, and it doubles as protection against a scan matching `X = …` inside an embedded code template.

### Changed

- **`lib/download.ts`'s `triggerDownload` returns the object URL it minted.** Purely additive — every existing caller ignores it. It exists for the one caller that gates a destructive action on the download having happened at all, and its doc comment is explicit that this is a handoff receipt and **not** evidence the file reached disk.
- **`isRecordId` moved to `lib/salesforce-id.ts`.** The SOQL runner's cell-menu heuristic (15–18 base-62 characters, not a `000…` blank key, a digit in the first five) is now the same predicate that decides which rows a bulk delete may touch. Two copies of a rule that gates a destructive action is the kind of duplication that drifts silently.
- **The SOQL runner uses `lib/download.ts`.** It still carried its own copy of the blob dance that module exists to replace — the same eight lines, in the file that also holds the two largest exports in the extension.
- **`renderSfError()` — one helper renders a Salesforce error, and nothing else may.** The previous shared builder took a single string, which was the affordance behind the sixteen one-by-one fixes in the last release: with the org's own text and our "what to do" line joined into one string, keeping them apart was a `white-space` rule each surface had to remember, and several instead resolved the ambiguity by throwing the org's real error away. `renderSfError()` / `setSfError()` emit the two as separate element nodes, so a block box cannot run into the one above it whatever CSS the host page brings, and a caller can no longer keep the wrong half because it no longer does the joining. The two halves travel **as structure**, not as a string to be re-parsed: `lib/sf-error-guidance.ts` composes them (`buildUserFacingParts`), `SalesforceRestError` carries them on `.userFacing`, and the renderer reads them back. Splitting the flattened message on newlines was the obvious shortcut and it is wrong — the org's own message can be multi-line (an Apex compile error is), so "everything after line one is ours" re-labels the org's continuation lines as our advice and paints them in our colour, which is the same defect inverted. Where an error carried no structure — a plain string, a `TypeError` — the renderer emits one node and guesses nothing. The corollary for callers: **pass the error, not `err.message`**; the three `showError()` funnels now take `unknown` for exactly this reason, and where a surface wants a line of its own beside the error it passes `guidance` rather than concatenating — which is how the REST and SOAP explorers now report an unparseable request body. Our guidance also stops rendering in the org's alarm colour — advice in the same red as the failure reads as more of the failure rather than as the way out of it.
- **The destructive-manifest banner is a callout, not an error console.** It carries our own warning prose, not an org error, which `lib/ui-styles.ts` has always distinguished at `.sfdt-callout`; wearing the error console's classes made the one *static* banner in the extension look like a live Salesforce failure and dragged it into every sweep aimed at the org-error path.

### Fixed

- **An Org Health check that fails now shows the org's guidance on its own line.** `lib/salesforce-api.ts` throws a two-line message — the org's own text, then the "what to do" line that `lib/sf-error-guidance.ts` appends — and Org Health folds it into a check's `summary` as `Could not run: …`. That summary was rendered into a span wearing only `.sfdt-muted`, which declares a font and a colour and no `white-space` rule, so the guidance ran into the org's text on screen. Both renderers are fixed — the live in-browser rows in `features/org-health-checks.ts` and the CLI-snapshot rows in `features/org-health.ts`, which are the same field rendered the same way — and both are pinned by rendered-DOM tests that read the qualifying classes out of the sheet rather than naming one. This is #308 inside the newlines guard's own scanned directories: the guard could not see it because `summary` is a struct field written in one function and read in another, and the widening that would reach it was built and measured (it claims every named property in the tree, turns rule 3's offender set from empty into seven false positives on correct code, and still misses the CLI half) and is therefore declined on the record, with the shape pinned by a test.
- **The options page shows an org failure on more than one line.** The bridge **Test connection** control and the **Save** handler both render an org failure into a `.status` span, and that rule declared a font, a padding and no `white-space` — so the "what to do" line `lib/sf-error-guidance.ts` appends ran into the org's own text, the same defect as the Org Health row above and on a surface two rounds of that fix never looked at. It was invisible to the guard for two compounding reasons, each of which hid the other: the newlines guard scanned `features` + `ui` only, so `entrypoints/` was out of range, **and** its file walk was `readdirSync` with no recursion, so adding the directory would have changed nothing on its own — every full-page surface is a subdirectory. Both are fixed, the guard now scans the same four directories its two sibling guards already did, and it reports these two sites without them. A third gap surfaced immediately behind that one: a page that owns its whole document declares `white-space` in its **own** stylesheet rather than through the shared `sfdt-` classes, which the guard did not read, so such a page could not satisfy the contract by any honest means — it now reads the file's own sheet, while still requiring the element to wear the class.
- **`Promise.allSettled`'s rejection reason is recognised as a thrown error.** `reason` is deliberately off the spelling list — `ui/apex-log-analyzer.ts` names a log-truncation reason `reason` — and the module justified that with "as a `catch` binding they are reached by the catch clause". That is false for this one: `PromiseRejectedResult.reason` is a property name the language mandates, so no catch clause binds it and nothing else reached it either. It was not a live hole only because `features/org-health-checks.ts` happened to write the `instanceof Error ?` form, which matches on the idiom; simplifying that one line to `String(s.reason)` took the site dark on every rule at once. The scan now recognises it structurally, scoped to files that provably handle settled results (`Promise.allSettled(`, or the `.status === 'rejected'` narrowing TypeScript requires before `.reason` is reachable). Measured tree-wide: zero new reported sites.
- **The source mask fails closed instead of silently blanking a file it could not read.** `dynamicParts()` asked `ts.createSourceFile()` for every literal span and never asked whether the parser had managed to read the source, so an unterminated comment returned a buffer of nothing but spaces — which every rule reads as a file containing no code. Green, silent, and the third time this guard has shipped that exact failure shape. It now refuses, with a message, on the two things that can actually run a mask past its target: a literal the scanner marks unterminated, and a block comment whose close is never found. Deliberately not "any parse diagnostic" — the mask is fed expression fragments as well as whole files, and 385 of those legitimately carry one. The suite also asserts that every scanned file parses with zero diagnostics, which until now was true only because CI happens to run `tsc --noEmit` before the tests.
- **The source mask no longer manufactures the very thing it refuses on.** Blanking a string literal's interior replaced every character with a space while preserving newlines — and a backslash immediately before a line break is a **LineContinuation**, legal ES and legal TS, and the only thing holding a quoted string open across that break. Eating it left an unterminated string the author never wrote, so masking the mask's own output threw; and the guards mask their own output constantly, because `readExpression()` cuts fragments out of the masked buffer. One three-line legal file in `features/` took the three guard suites from 52 passing to 6 failing. Continuations are now kept verbatim — backslash and terminator — which preserves every offset and line number and leaves a literal that still closes, with escapes tracked so a genuinely unterminated string is still refused. The property is asserted rather than asserted-about: whatever the mask accepts it must accept again with the same answer, over every scanned file, over every scanned file with a continuation spliced in, and over a corpus of legal-but-hostile constructs whose legality is checked against the compiler first.
- **The sweep now reads the name a `for-of` head binds.** The binding scan looked for `(const|let|var) NAME … =`, and a for-of head has no `=` — so `for (const line of String(err).split('\n')) pane.textContent = line;` bound nothing and all three rules went quiet on `line`, while the same value one line later through `const line = …` was caught. 265 such heads in the scanned tree made it the largest gap the guard had. The element now inherits from the iterable through two questions, each asked in the position it was written for: the receiver of a top-level `.split()`/`.match()` is a **string**, so if it carries an error every element is a piece of that text; and a member chain whose last non-call link is error-ish (`err.errors`, `err.errors.filter(Boolean)`) is a **collection of errors**, so every element is an error that has not been stringified — which keeps `renderSfError(sub)` the correct call it is. Arguments never contribute and a ternary is not a collection, so how a collection was **built** can no longer be mistaken for what is **in** it. Measured tree-wide before it was committed to: the same 11 binding names, the same per-file lists, the same 12 reported sites, no new offender anywhere.
- **The mask's caches are bounded in bytes, not just in entries.** Three caches of 8,192 entries each, where an entry is a whole source file, is hundreds of megabytes; the tree-wide backtick property took the worker to 1.1 GB before this. Now a 4 MB budget per cache, which keeps the hit rate that matters (the same handful of whole files, over and over) and cannot grow without limit.
- **A thrown error with no message renders a panel again, instead of nothing.** `sfErrorParts()` falls back to `errorText()`, which is `''` for `new Error('')` or a bare `throw new Error()` — so `setSfError` found no parts, took the branch meant for `renderSfError(null)`, and cleared the pane. A caught failure with an empty message therefore arrived as no panel, no `role="alert"` and no text, from every call site that forwards a caught error. That is the defect PR #308 existed to remove, reintroduced through the null contract the shared helper brought with it, and invisible to the source sweep because every call site is *correct*. `null`/`undefined` still render nothing — a caller saying "there is no error" is a different statement from an error saying nothing.
- **The source sweep could be blinded, over an arbitrary span, by one backtick.** The mask both guards read the tree through treated every backtick as a template delimiter and — unlike its `'`/`"` branch — did not stop at a newline. A backtick that opens no template (a markdown fence in a comment, a `` don`t ``, a `` /[`]/ `` in a regex) started a mask running to the next backtick anywhere in the file. Measured on `features/rest-explore.ts`: one backtick appended to the header comment at line 38 blanked 7,588 characters through to line 108 and took the file's only `.textContent =` with it — rules 2 and 3 and the whole newlines guard silent over seventy lines of a live feature file, with nothing failing. 93 of 125 scanned files carry backticks inside comments, 1,819 in total, balanced today by convention alone. The mask now asks the TypeScript parser where a literal starts and stops instead of scanning characters, so it cannot be defeated by an odd backtick, and it drops comments and regex literals as well as literal prose. A tree-wide property pins it: injecting a backtick into a comment must not change what any file looks like to any rule.
- **The sweep now sees `.catch((e) => …)`, not only `try/catch`.** The binding scan matched `catch (` followed directly by a name, so the statement form was read and the promise form was not — and with Prettier's `arrowParens: "always"` default the parenthesised form is the only one `prettier --write` will ever emit for a single parameter. The two sites in the tree that write it happen to be spelled `err`, so the spelling fallback was quietly covering the gap. `async` and `function` handler heads are read through too.
- **The exemption list on the newlines guard is held to what an exemption actually claims.** Its bite check asserted that the assignment still existed and that the expression looked error-ish — neither of which is "this site would be reported without me". Any site already covered by a class, a `cssText` rule or a panel builder could therefore be exempted for free: a decorative `ui/toast.ts` entry was accepted in review while `ui/toast.ts` carries `white-space: pre-line` and is provably not an offender. The check now re-runs the real offender scan with the entry removed and requires the site to appear, which is the shape the sibling exclusion check on the sweep already had.
- **Escape inside a confirm dialog no longer closes the modal behind it too.** `ui/present-view.ts` also listens for Escape on the document and defers only to other `.sfdt-view-overlay`s — it cannot see a confirm dialog stacked above it — so one Escape aimed at "cancel this delete" also tore down the view underneath and took whatever was typed into it (in the SOQL runner, your query). The dialog now consumes the key from the capture phase, which is exactly what `ui/menu.ts` already does and what present-view's own comment names as the reason it never sees a menu's Escape. Affects every confirm: Debug Logs' delete-all and the Flow version manager's too.
- **A confirm dialog whose trigger was disabled sent focus to `<body>`.** Focus is restored to whatever was focused when the dialog opened, and a **disabled element cannot receive focus** — so the common shape of `btn.disabled = true; await confirmDialog(…)` silently stranded keyboard users. `confirm-dialog.ts` now documents the caller contract and `test/confirm-dialog.test.ts` pins both halves of it, because nothing can be fixed inside the dialog: `.focus()` on a disabled element is a specified no-op. The bulk delete disables its trigger only once the destructive phase actually starts (re-entrancy in the meantime is a flag, and the modal's own scrim and focus trap already make the trigger unreachable). `features/debug-log-viewer.ts` had the original shape and is fixed in the same release — see *Delete all debug logs returns focus* below.
- **Delete all debug logs returns focus to the button you pressed.** The trigger was disabled across the count fetch *and* the confirm dialog, and a disabled element cannot take focus back — so cancelling that dialog left keyboard and screen-reader users on `<body>`, the same defect the bulk delete fixed. Moving one line was not available: the count is a genuinely slow paginated fetch that needs a busy affordance. The busy state now belongs to the fetch and ends with it, the destructive phase gets its own, re-entrancy is a flag rather than `disabled`, and the focus the disable itself cost is handed back before anything can open a dialog.
- **Stopping a bulk delete no longer looks like a success.** A cancelled run with no failures showed a green *Deleted 25 Account record(s)* toast, no report panel at all, and logged `success` in the activity log — so the report's *Canceled before the remaining rows were attempted* line stayed unreachable in the common case. A stopped run now warns, shows the report, and is not recorded as having done what you asked. And when the stop came from running a **new query**, none of it is written against the table: that result set has already been replaced, so `Deleted 25 of 60 · re-run the query to refresh the table` was describing rows that are no longer on screen and advising the user to do the thing they had just done. It is a toast instead.
- **The Delete button's tooltip no longer promises a download it cannot see.** It said *Downloads a backup CSV*; everywhere else — the dialog, the docs site — says the CSV is generated and handed to your browser and that SFDT cannot confirm it reached your disk. The one spot the copy sweep missed, on the control whose whole safety story is the backup.
- **`1 failed — 1 failed.`** The per-row report's summary reads `${count} ${label}`, under a lead-in that already gives the count, and the `unknown` kind's label was the word *failed*. It is *unclassified* now, and when that is the only kind the breakdown is dropped entirely — the per-row lines below it carry the real message.
- **`planBulkDelete()` drops rows that disagree with an explicit `sobject`.** Its doc contract said rows disagreeing with `opts.sobject` "are dropped rather than silently deleted against the wrong object", and the code never compared the two — the declared name was used unconditionally, so the guard the comment described did not exist. Not exploitable today, for two reasons external to the function: the only caller passing `sobject` is the SOSL group toolbar, whose rows are already grouped by `attributes.type`, and Salesforce rejects a `DELETE` whose Id key-prefix does not match the sObject in the path. Neither fact is visible from inside `planBulkDelete()`, which is the problem — the next caller reads the contract, trusts it, and inherits a filter that does nothing. Implemented rather than downgrading the comment: the rest of the function plans defensively on purpose (it re-plans from raw records precisely so a caller cannot widen the set), so a caller-trusting exception here was the inconsistency. A row carrying no envelope still takes the declared name — that is what `opts.sobject` exists for, since the SOSL groups strip `attributes`.
- **A Salesforce error is announced to screen readers, on every surface.** Fifteen features built the org-error panel by hand — `createElement('div')`, `classList.add('sfdt-console', 'sfdt-error')`, `textContent = err.message` — and every one of them set the classes and left off `role="alert"`. A failed query, retrieve or test run was a red box to a sighted user and complete silence to anyone using a screen reader. All fifteen now come from one builder, which cannot forget the role. The panes that are *reused* (the debug-log console, the Execute Anonymous result pane) also give the role back when they stop carrying an error, or the next successful run would be announced as a failure — and an empty panel never carries it at all, since a live announcement region sitting in the tree claims whatever lands in it next.
- **Two org errors that had no error styling at all.** Execute Anonymous's "Open log" button and the Flow AI assistant's metadata fetch each wrote a live Tooling failure into the page as bare text: no red, no border, no `role="alert"`. In the Apex log pane that made a permissions failure indistinguishable from a log body. Neither was reachable by the guards the last release added — the pane already wore the class those guards check — which is why the new sweep carries a second rule aimed squarely at this shape.
- **A third and fourth org error with no error styling — both found by the sweep, once it could see them.** The Platform-Event limits pane (`features/event-monitor.ts`) rendered a caught failure as bare text into a hand-styled `div`: no class, no `role="alert"`, no `white-space` rule, so the guidance line collapsed into the org's text and a screen reader announced nothing. - **Feature kill switches now apply to the Workspace and the docked side panel.** Turning a tool off in Settings removed it from the ⚡ menu on Salesforce pages (`entrypoints/content.ts` gates on `isFeatureEnabled`) but the Workspace built its sidebar straight from `WORKSPACE_TOOLS` with no reference to settings, so the tool stayed visible and usable there. - **The Workspace's synthetic window threw `Illegal invocation` on any WebIDL accessor.** `makeSyntheticWin` forwarded the *proxy* as the `Reflect.get` receiver, so reading `scrollY`, `innerWidth` or any other `Window.prototype` getter through it ran that getter with `this` = proxy — which Chrome rejects. - **An extension update no longer leaves open Salesforce tabs throwing `Extension context invalidated`.** Chrome updates an extension underneath tabs that are already open, which orphans the content script running in them: the page keeps executing it, but its `chrome.*` handles are dead and the next call throws. Nothing in the extension can rescue an orphaned script — the tab has to be reloaded — but every storage touch was throwing uncaught instead of failing quietly, so a routine Web Store update turned each open Salesforce tab into a console full of errors. Storage now goes through `lib/storage.ts`, which returns the same fallback an unset key does: reads resolve `undefined` (so settings fall back to schema defaults, the kill-switch cache reports nothing disabled — failing *open*, since failing closed would disable every tool in the tab — and recents and the activity log read empty), writes report `false` rather than throwing, and unsubscribing after the context dies is a no-op. Two things the previous ad-hoc guards got wrong are handled here: the throw is *synchronous*, so wrapping the promise body would only have converted an uncaught error into an unhandled rejection; and a quota failure arrives *asynchronously* on `runtime.lastError` with the callback still firing, which a `try`/`catch` alone reports as a successful save. `test/storage.test.ts` simulates the orphaned context and fails against the unguarded code.
- **The SOQL runner's record-Id menu leaked a listener on every use.** It bound a `document` click listener each time it opened and removed it only on outside-click — so *choosing* an item leaked one, permanently, once per record Id you ever clicked. It is now built on `ui/menu.ts`, which tears both listeners down on every exit path.

Both are real buttons now, with `aria-haspopup`, menu semantics and Esc. - **The Event Streaming Monitor was broken outright in Chrome.** `SalesforceBayeuxClient` held `fetch` as a property and called it as `this.fetchImpl(url)`. `fetch` brand-checks its receiver, so with the client instance as `this` Chrome refused: `Failed to execute 'fetch' on 'WorkerGlobalScope': Illegal invocation`. `lib/sf-api-proxy.ts` holds the same value from the same caller and was fine, because it calls it bare. It is now bound to the global in the constructor, so a future `this.fetchImpl` is safe by construction. Every test in the file passed with the bug present — an ordinary `vi.fn()` brand-checks nothing — so the test now asserts the **receiver**.

Five features had their own download dance and two never called `revokeObjectURL`: the failed-row error CSV in Data Import (leaked per export) and Metadata Retrieve, which leaked twice — including the retrieved zip, routinely tens of megabytes. ### Fixed
- **"Session expired or invalid" no longer appears in place of the error Salesforce actually sent — and errors now tell you what to do about them.** Running a query with a type mismatch in the `WHERE` clause (`… WHERE Invoice_Status_Type__c = 'Chargeback'` against a numeric field) showed one red line — **"Salesforce GET request failed (HTTP 401): Session expired or invalid"** — on a session that was perfectly healthy, while the org's real answer (HTTP 400 `MALFORMED_QUERY`, naming the field and saying the value must not be quoted) was discarded before it ever left the extension. **The mechanism:** after any prior successful call the worker caches which of your org's two host names served it, and sends the next request straight there. When the **org** rejected that request — a 400/404/FLS refusal, i.e. Salesforce answering the question you asked — the fast path treated it like a dead host and retried the whole request against the other candidate. That candidate is `lightning.force.com`, which routinely answers 401 for REST, and **only that 401 was returned**; the original error was dropped. So the failure needed nothing more exotic than a warm session — which is why it was also reported on **Data Import**'s CSV path, and why it could hit any feature. A failing response whose **body is actually a Salesforce error** (a REST error record or a SOAP fault) is now recognised as the org answering rather than the transport failing, and is returned verbatim. The test is the body and not the status, because a status code cannot tell the two apart — a 403 is Salesforce denying access when Salesforce sends it and a block page when a corporate proxy sends it — so an opaque 4xx from an intermediary still falls back to the other host exactly as before. 401/5xx/network errors likewise still fall back, but the first failure is now carried alongside rather than replaced. As a side effect a write the org has already rejected is no longer re-sent to the second host. **Separately, every org error now explains itself.** Salesforce's rejection bodies carry an `errorCode` and the `fields[]` the org blamed, and both were being flattened away into a single line. Errors now lead with **the org's own message, unchanged**, then add the error code, the field(s) named, and a short "what to do" line for the codes people actually hit — `MALFORMED_QUERY`, `INVALID_FIELD`, `INVALID_TYPE`, `INVALID_SESSION_ID`, `REQUEST_LIMIT_EXCEEDED`, the FLS/permission denials, validation-rule failures, row locks and ~15 more. An **unrecognised** code still renders the org's message and the code in full: an unknown code means we have no advice to add, never that we substitute something generic. Nothing is inferred — session advice can only ever attach to an error the org itself tagged as a session problem, which is the whole point of the bug above. SOAP faults reuse the same table via their `faultcode`, which is what **Data Import** batch failures and **Metadata Retrieve** surface. Two further places that had been throwing the org's error away entirely are fixed with it: **Field Creator**'s object-list load showed only "Failed to load SObject list" (it could be a disabled API, a profile with no createable object, or a genuinely expired session — never said which), **Inspect Record**'s lookup navigation showed only "Navigation failed" (usually: you cannot read the referenced record), and a failed describe recorded only that it failed, so the **Schema Browser** and the SOQL Runner's autocomplete could offer nothing but a retry button and no reason to think retrying would help.
- **Writes no longer give up after 5 seconds and blame your session for it.** Every call through `lib/salesforce-api.ts` inherited one blanket 5-second budget for the background worker to answer, and a blown budget resolved `null` — which the client could not tell apart from "the worker has no session", so it threw **"No Salesforce session available"**. Two things were wrong with that. The budget was far too short for real work: **Field Creator** (Tooling `CustomField` create + FLS grants), **Data Import** (Partner-SOAP `create`/`update`/`upsert` batches), **Execute Anonymous** (which also creates a `DebugLevel` and a `TraceFlag`), plus trace-flag management, bulk log deletes, record edits and the REST Explorer all routinely exceed five seconds on a busy org. And the message was a false diagnosis: the session was fine, so anyone who acted on it went off to re-authenticate for nothing. Worst of all, it was **dangerous on a write** — the request had usually already committed server-side, so the UI reported a failure for a change that had actually landed, and retrying created a duplicate. Reads now get **30s** (above the real duration of a large describe or a multi-MB `ApexLog` body, still fast enough to be actionable) and writes — every `POST`/`PATCH`/`PUT`/`DELETE`, plus any SOAP call its caller declares as writing — get **120s**, matching the platform's own ceiling for the longest synchronous operation these paths trigger. SOAP tunnels reads and writes through one POST, so `apiSoap` now takes an explicit `mutating` option that each call site declares: `Metadata.deploy` and Data Import's Partner `create`/`update`/`upsert`/`delete` are writes, while `describeMetadata`, `listMetadata`, `retrieve`, `checkRetrieveStatus` and `checkDeployStatus` are reads. That last one matters most — it is polled in a loop, so treating it as a write would have told the user their change "may already have been saved" once per poll of a slow deploy, for a call that wrote nothing. An undeclared caller defaults to *writing*, the safe direction (SOAP Explorer sends a user-typed operation and genuinely cannot know). A blown budget is now reported as what it is: reads say *"…timed out after 30s — the extension's background worker did not answer. This is a timeout, not a lost session; retry the request."*, and writes refuse to claim the operation failed, saying instead that **the result is unknown and the change may already have been saved, so check before retrying to avoid duplicating it**. The 401-retry, dual-host fallback, and SID-never-leaves-the-worker behaviour are all untouched.
- **API failures now carry a machine-readable reason, not just prose.** Every error thrown by the Salesforce client is tagged with a stable `sfdtKind` discriminant — `'timeout'` (outcome **unknown**; `mutating` says whether data could have changed, `timeoutMs` carries the budget that elapsed), `'no-session'` (the request definitely did not run), or `'http-error'` (Salesforce answered with a failing `status`) — readable via the exported `sfApiErrorKind(err)` helper. `sfdtKind === 'timeout' && mutating === true` is the **only** combination that means "this may have committed", which is why SOAP declares `mutating` per call site rather than wholesale — a slow status poll must not be able to produce it. This is purely additive: the `message` text of the no-session and HTTP-error cases is byte-identical to what shipped, so anything that only renders `err.message` is unaffected. It exists so callers that need to distinguish "definitely failed" from "may have committed" can branch in code rather than pattern-matching English.
- **A feature manifest's `enabledByDefault` is now authoritative at runtime.** The flag was declared on `FeatureManifest`, carried through to `lib/feature-manifests.json` and `generated/chrome-features.json`, and asserted in the manifest parity test — but nothing ever read it when deciding whether a feature should run. `isFeatureEnabled()` returned a blanket `true` for any id with no stored preference, so a feature could only ship **on**; declaring `enabledByDefault: false` had no effect whatsoever. The default now comes from the feature's own manifest (`enabledByDefault ?? true`) via the new `lib/feature-defaults.ts`, which is seeded at import time from the checked-in `feature-manifests.json` — so it is correct in surfaces that never build a registry, notably the service worker gating the right-click "Inspect this record" menu — and additionally fed by `FeatureRegistry.register()` for features constructed at runtime (the Workspace host). **Precedence is unchanged where it already existed and is now pinned by tests:** an explicit user toggle (canonical or legacy camelCase id) always beats the manifest default in *both* directions, so anyone who previously switched a feature off stays off and anyone who switched one on stays on; the remote kill switch still overrides both. **No shipped feature changes behaviour** — every shipped manifest declares `enabledByDefault: true`, which the new parity suite asserts feature-by-feature (both that none declares `false`, and that every one resolves to enabled for a user with no stored preferences) so a future `false` cannot silently disable a feature for existing users. No new permissions, no new runtime dependencies. The JSON seed's *value* mapping is pinned by a mocked-manifest fixture (`test/feature-defaults.test.ts`) declaring `enabledByDefault: false` — the one input the real shipped corpus cannot supply, since every shipped entry is `true`.
- **Every SOAP call was going to a malformed URL.** The five SOAP service paths were built by concatenating the client's `apiVersion` onto the service prefix — but `SF_API_VERSION` ships **with** its `v` prefix (`v62.0`), because that is the form REST paths need. SOAP service paths take a **bare** version, so the extension asked for `/services/Soap/m/v62.0` and Salesforce refused it outright with `Invalid Api version specified on URL : /m/v62.0`. That is not one feature — it is every SOAP surface the extension has: **Metadata Retrieve & Deploy**'s offline SOAP path (`describeMetadata`, `listMetadata`, `retrieve`, `deploy`, and their status polls), the **SOAP API Explorer**, and **Data Import**'s Partner `create`/`update`/`upsert` batches. The bug was long-standing rather than new — the `final_14` store screenshot captured the error live — and it broke retrieve and deploy on **both** of Metadata Retrieve & Deploy's data paths, not just the offline one. The bridge kinds `manifest.discover` / `manifest.render` cover type discovery and manifest XML only; there is no retrieve or deploy kind in the bridge contract, so `retrieve`, `deploy`, `checkRetrieveStatus` and `checkDeployStatus` run over SOAP unconditionally whether or not a bridge is connected. In 0.10.0 a bridge-connected user could therefore browse metadata types and preview a manifest, but could not perform either of the two operations the feature is named for; an offline user could not do any of it, since `describeMetadata` and `listMetadata` are SOAP too. The `v` is now stripped for the SOAP path only, leaving REST paths byte-identical, and the resulting path is pinned per service (`Enterprise` `/c/`, `Partner` `/u/`, `Apex` `/s/`, `Metadata` `/m/`, `Tooling` `/T/`) by tests, so the two version formats cannot be confused again.

### Added
- **Field Impact Analysis — "what writes this field?" (P4-4).** A new `field-impact` feature answers the question a schema browser never could: *which automation actually writes `Account.Industry__c`?* It is reachable from the two places a user already has a field in front of them — a per-field **"What writes this?"** action in the **Schema Browser**'s field table, and a labelled field picker in the **Show API Names** panel — plus standalone from the Workspace and the ⚡ menu. Three sources are gathered: **Flows**, via `@sfdt/flow-core`'s new `extractFieldWrites` (`MetadataComponentDependency` narrows the candidate set, then flow-core decides which of those candidates *write* the field rather than merely reference it — a flow that only reads it is dropped, which a raw dependency query cannot do); **workflow field updates**, from Tooling `WorkflowFieldUpdate.Metadata.field`; and **Apex**, from a best-effort Tooling SOSL text search over class and trigger source. Every row is badged **confirmed** or **inferred** using the same vocabulary as the dependency `--gaps` report — confirmed means the metadata states the write (a parsed Flow assignment/inputAssignment, a field update naming the field), inferred means a best-effort signal (an Apex text hit, a candidate flow we did not analyse, a Flow write whose object could not be bound). An inferred hit is never presented as confirmed: the status is the badge's own text (not colour alone), the counts are reported separately in an `aria-live` summary, and the legend spells both out. Scan bounds AND scan precision are stated rather than hidden. A standard field has no `CustomField` row and therefore no dependency edge to narrow by, so Flow coverage falls back to a broad sweep of the most recently modified active flows — and on that path a flow is reported **only** when its own metadata binds the write to the queried object, with no exceptions. A write into an untyped or Apex-defined variable is skipped rather than guessed at, because matching on the bare field name would attribute any flow writing some *other* object's `Status`/`Type`/`Rating` to yours. **A flow whose metadata could not be read at all is likewise not listed on that path** — nothing linked it to the field in the first place, so a row would assert a reference that was never established (on the dependency-narrowed path the edge *does* establish it, so there the flow stays as an inferred lead). Either way the drop is counted and explained in the note rather than performed silently. The note is also careful not to overstate *why* the broad scan happened: only a dependency query that actually ran and came back empty is reported as "no dependency edge was found", while a standard field, a missing `CustomField` record and a refused lookup each say which of those it was. The "Scan scope" note states both that rule and the results it consequently omits. (The lenient keep-it-as-inferred behaviour is retained on the dependency-narrowed path, where something has already established that the flow references this field.) Per-cap skips and degraded queries are disclosed the same way, including the Apex search's true bound — SOSL applies a trailing `LIMIT` per returned sObject type, so the cap is enforced client-side after a deterministic sort, and when it truncates the note reports how many rows were **returned** while saying plainly that this is itself a capped number rather than the true match count. **The disclosure is symmetric and it never overstates what was established.** The dependency-narrowed path says so too (writes it cannot bind are kept as inferred leads, and results from the two paths are not directly comparable), so a user is never left guessing which rule produced their answer. A query the org **refuses** is named with its reason and is never reported as a finding: a failed `CustomField` or `MetadataComponentDependency` lookup says the scan could not be narrowed, rather than asserting "no dependency edge" — a claim that was never established and that also silently selects the stricter rule. Workflow field updates whose `Metadata` comes back unreadable are counted and explained rather than appearing as unexplained inferred rows. The panel also states the **parser's own** bound whenever a flow was parsed: Create/Update Records assignments and `<record>.<Field>` Assignments are analysed, while Transform elements, invocable/quick actions and subflow bodies are not, so a flow writing the field only that way is missing from the results. And because a *negative* result is the dangerous one — the table is empty, so only the `aria-live` summary is announced — an empty result whose scan carried any caveat hedges the announced sentence itself ("…in the scanned set — this was a partial scan that can exclude real writers; see Scan scope below") instead of leaving the qualifier in a panel a screen-reader user is never told about. Every row carries an Open link (Flow Builder, or the Setup page for the class/trigger/field update). All org calls go through the worker-proxied API; there is **no second Flow parser in the extension** and **no new manifest permission**.
- **Groundwork for record edit / clone: a shared editability model and typed API errors (P4-1, PR-1). No user-visible change in this version** — nothing renders it yet; it ships tested so the edit path built on top of it has one contract to obey rather than several. Three pieces. (1) A **structured REST error**: a Salesforce rejection body names the field the org refused (`[{"message":…,"errorCode":"STRING_TOO_LONG","fields":["Name"]}]`), and that `fields`/`errorCode` pair was flattened into one prose string and dropped, so no caller could put an error on the field it belongs to. `SalesforceRestError` now carries the parsed records alongside `status`; `.message`, `sfdtKind` and `.status` are byte-identical to what shipped, so no existing call site changes. (One thing that *is* different: `.name` is now `SalesforceRestError` rather than `Error`, so `String(err)` gains that prefix. Every consumer in the tree renders `err.message`, not the stringified error, so nothing changes on screen — but it is a real difference and "purely additive" should not be read as hiding it.) A non-JSON body (a 503 HTML page), a bare object instead of an array, or a record with no `message` all degrade to an empty list rather than throwing. (2) The **edit-relevant describe attributes** (`updateable`, `createable`, `autoNumber`, `htmlFormatted`, `encrypted`, `restrictedPicklist`, `dependentPicklist`, `controllerName`) are declared on the shared `FieldDescribe` — types only, since the describe cache already stores the payload wholesale, and now pinned by a test so a future refactor cannot drop them. (3) **`lib/record-edit.ts`**, pure and DOM-free, which answers three questions once each. *May this field be written* — by a rule, not a taste list: a field is editable only where the DOM offers a native lossless control and the wire format is unambiguous, and everything else gets a stated reason (calculated, auto-number, system, unsupported type, or a deliberately non-committal "not editable for you", because describe is evaluated per user and we do not assert a cause we cannot verify). *What goes on the wire* — with `date` handled as text and never parsed through a `Date`, so it cannot shift a day for anyone west of UTC; `datetime` and `time` carrying their seconds and milliseconds through the control, so reading a record and saving it without touching anything cannot quietly zero a field's seconds; and unparseable numeric text handed to the org rather than guessed at, so the user gets a precise field-level error instead of a silent local one. *What changed* — one diff builder feeding both the save bar and the PATCH body, where today two independent comparison loops answer that separately and can disagree. It compares in canonical form, so `3` vs `'3'`, `''` vs `null`, two spellings of one instant, and a multi-select picklist whose values merely come back in a different order are all correctly no change; and it **omits any field absent from the record payload the org returned**, because a field hidden from you by field-level security arrives as nothing at all — indistinguishable, to a naive comparison, from a field you just cleared, and including it would write `null` over a value you were never shown. A field that is merely empty is present, and stays editable. No new permissions, no new dependencies.
- **SOSL mode in the SOQL Runner (P4-3).** The runner's toolbar gains a **SOQL | SOSL** toggle — a real radiogroup (`role="radiogroup"` + `role="radio"`/`aria-checked`, roving tabindex, arrow-key selection) — and the mode also auto-follows what you type: a query whose first keyword is `FIND` switches to SOSL and a `SELECT` switches back, the same auto-routing the `sfdt ui` SOQL console already does. An **explicit click wins over that inference** — pick a mode and it holds through further edits of the same query, until the query's own language actually changes. Detection is one rule (`/^\s*find\b/i`) shared with the CLI's `sfdt soql` (`validateLocal`), so a query that runs as SOSL in the terminal runs as SOSL here. **SOSL results are grouped per returned sObject**, one labelled section each (`Account · 2 rows`) with its own table, and each group carries the **same result toolbar** as a SOQL result set — Copy CSV, Export CSV, Copy JSON, Copy for Excel — scoped to that group's rows, so copy/export apply per object. There is one toolbar definition and one set of serialisers behind it (the P1-3 `recordsToCsv`/`recordsToJson`/`recordsToTsv`); the group buttons keep the same visible labels but get per-object accessible names ("Copy Account rows as CSV") and a per-object export filename (`sosl-Account-<stamp>.csv`). **History and bookmarks now record the query language** and restore it: picking a SOSL entry from History or Bookmarks — or staging one from the Saved SOQL panel — puts the editor back in SOSL mode, and both menus badge each entry `SOQL`/`SOSL`. Entries saved before this version carry no language and fall back to detection from their text, so an old `FIND {…}` bookmark still restores correctly. In SOSL mode the **transport toggle reads as unavailable** (disabled, with a title saying why) and **Explain** is disabled — the Search resource has no Tooling variant and no query plan, and the GUI console disables Plan for a FIND query too. Crucially your REST/Tooling choice is **preserved, not reset**: SOSL runs on REST because that is the only thing it can run on, and switching back to SOQL — or merely pasting a `FIND` query to look at it — leaves you on Tooling if that is where you were. History records the transport that actually ran. The SOQL autocomplete box is hidden rather than offering SELECT/FROM suggestions for a search. SOSL goes over the same worker-proxied REST call as everything else; **no new permissions, no new dependencies**.

### Fixed
- **Restoring a member-level selection no longer truncates that metadata type's tree.** `restoreSelections()` seeds the persisted member into the type's children, but the member-fetch guard in `toggleExpand()` tested *emptiness* (`childXmlNames.length === 0`) rather than *completeness* — so after reopening the tool, a type with a restored member showed **only** that member, forever: collapsing and re-expanding never re-fetched, and there is no refresh affordance, so the only way to see the type's other members was to drop the saved selection. Load state is now tracked explicitly (`membersLoaded`, set only by a successful bridge/SOAP member fetch), so a node whose children came from storage — or from an imported `package.xml`, which had the same defect — still fetches its real member list on expand, while a genuinely loaded node does not re-fetch. The restored ticks survive that fetch: they are merged onto the fetched list, and a selected member the org no longer returns is **kept** (with a log line naming it) rather than silently dropped, since not losing the user's selection is the entire point of persistence. A restored type is also left **collapsed** rather than expanded, so a one-member list is never *presented* as the type's complete membership and the first expand does the real fetch — no hidden collapse-then-expand needed; the type row carries a **partial tick** (`indeterminate`, labelled "some members selected") so the restored selection is still plainly visible while collapsed. Fixed on both the bridge and offline SOAP paths. Wildcard restores were never affected (they set the type's own tick and never touch the child list).
- **A `manifest.discover` reply missing its `members` array is treated as a failure, not an empty metadata type.** The bridge branch coerced a non-array payload to `[]` *and* marked the node loaded, so a malformed `ok: true` response produced a fabricated empty tree that then never re-fetched — precisely the failure the "never a fabricated empty tree" invariant exists to prevent. Such a response now surfaces as an error, collapses the node, and leaves it re-fetchable with its seeded children and ticks intact. (The offline SOAP path has no equivalent hole: `apiSoap` throws on every transport error and SOAP fault, so a falsy `listMetadata` result genuinely means the type has zero members — that is now documented in place.)
- **Expanding or collapsing a metadata type no longer costs a `manifest.render` round-trip.** `toggleExpand()` ended with an unconditional `onSelectionChanged()`, so every browse click re-rendered the manifest over the bridge and rewrote the persisted selection even though nothing had been selected. The manifest selection is now signature-compared across the toggle and the re-render/persist fires only when the effective selection actually moved (which the seeded-member merge above can legitimately do) — so the "preview updates on every selection change" contract is unchanged while plain browsing is free.

### Changed

Three declared keyboard commands are also added and are remappable at `chrome://extensions/shortcuts`: **Open Workspace** (`Ctrl/Cmd+Shift+E`), **Open quick menu** (`Ctrl/Cmd+Shift+K`, opens the ⚡ side menu until the command palette ships), and **Toggle inspector** (declared now; surfaces a "not available yet" notice until the LWC inspector lands). Because the commands are registered by the browser rather than by in-page keydown listeners, they work on a Salesforce tab even before the content script has finished loading. Session status is read in the service worker, never from the page, so the session cookie stays in the worker. No new permission is required — `commands` is a manifest key, not a permission.
- **Right-click "Inspect this record" context menu (P1-8).** Right-clicking a Salesforce page — or a link to a Salesforce record — now offers **"SFDT: Inspect this record"**, which opens the record inspector for the record Id found in the page URL or the right-clicked link's target. The item appears only on your Salesforce hosts (scoped via `documentUrlPatterns`/`targetUrlPatterns`) and does nothing when no 15/18-char record Id is present. It's a normal kill-switchable feature with an opt-in **Options → Features** toggle (enabled by default). The menu lives in the service worker and only ever forwards a record Id to the inspector — it reads no cookies or session data, so the `sid` stays in the worker. **Ledgered new manifest permission `contextMenus`** (documented in `PRIVACY.md` and the store listing); no other permission added.
- **SOQL Runner — Copy JSON + Copy for Excel.** The result toolbar gains two client-side copy actions alongside Copy/Export CSV: **Copy JSON** copies the currently displayed rows as a pretty-printed (2-space) JSON array (the Salesforce `attributes` envelope stripped so it matches the shown columns; nested relationship records keep their structure), and **Copy for Excel** copies them as tab-separated values with a header row that paste straight into a spreadsheet as columns. TSV values containing tabs, newlines, or quotes are quoted/escaped so a cell can't break the grid. Both operate purely on the already-fetched result set (the loaded pages, up to the pagination cap) with no extra org calls, and use `navigator.clipboard` (no new permission).

### Changed
- **Security posture: the Salesforce session id (`sid`) no longer enters page-adjacent memory.** Every REST/Tooling/SOAP call now runs inside the background service worker via a new `sfApiFetch` message route (`lib/sf-api-proxy.ts`): the worker reads the `sid` cookie, injects `Authorization`, performs the dual-host fallback + one-time 401 retry, and returns only the response *text* — never the sid. `lib/salesforce-api.ts` is now a thin client that describes the call and parses the reply; it holds no sid and makes no Salesforce fetch of its own. SOAP calls send a sentinel placeholder that the worker swaps for the real sid inside the `SessionHeader` only. Request headers are allowlisted (any client-supplied `Authorization` is stripped). A guard test (`test/sid-never-leaves-worker.test.ts`) plus a scoped ESLint rule enforce that feature/UI code never touches `chrome.cookies`, the `getSidForUrls` route, `getSessionDetails`, or a raw `Authorization: Bearer` header. Internal refactor — no user-facing behaviour change.
- **SID-in-worker migration complete — zero exceptions.** The Event Streaming Monitor's CometD/Bayeux long-poll (the last page-side holder of a raw `sid`) now runs entirely in the service worker behind a long-lived `sfApiStream` Port (`lib/sf-stream-worker.ts`). The feature opens the Port, sends `subscribe`/`unsubscribe`, and renders only the `status`/`event` messages the worker pushes back — the sid never reaches the page. The residual page-side session machinery (`getSession`/`getSessionDetails`/`getSidForUrls` client path) is deleted, and both the guard test and the ESLint rule now allowlist nothing (they also fail on any `getSessionDetails` reference). This completes the P0-4 "SID never leaves the worker" guarantee. On MV3 service-worker eviction the Port disconnects and the monitor shows "Disconnected" with Subscribe re-enabled, so the user can reconnect. No new manifest permission (`chrome.runtime.connect` is a platform primitive). Internal refactor — no user-facing behaviour change. (Re-landed onto `develop` after the original approved change was stranded by a squash-merge into an intermediate branch that never reached `develop`.)
- **Shadow-DOM host for injected UI (internal, no visual change).** All content-script-injected UI on a Salesforce page — the ⚡ side button and its menu, `present-view` page-mode modals, and toasts — now renders inside ONE shared **closed** shadow root (`ui/shadow-host.ts` + `ui/content-root.ts`), fully isolating it from the host page's CSS in both directions: Salesforce's global styles can't bleed into our overlays, and our styles can't leak onto the page. This cuts the per-release visual breakage caused by Salesforce DOM/CSS churn. Dark mode is unaffected — the `--sfdt-*` design tokens stay defined on the host `:root` (custom properties inherit across the shadow boundary), so `var(--sfdt-*)` still resolves and flipping `data-sfdt-theme` on the host still re-themes the overlays live. Click-outside dismissal now uses `composedPath()` so it works correctly across the shadow boundary; Esc/focus behaviour is unchanged. Our own full-page surfaces (the Workspace app + options page) are not injected into a hostile document and stay in light DOM. Realises CONVENTIONS.md item 13 (previously a documented gap).
- **Single Salesforce API-version constant.** Divergent `v62.0` literals across features are consolidated into one authoritative `SF_API_VERSION` (`lib/api-version.ts`), re-exported by the client as `api.apiVersion`.
- **Design-token refactor (internal, no visual change).** Every hard-coded colour across the content-script features, the Workspace app page, the options page, and the shared `ui/` components (~770 hex literals in 38 files) is now a `var(--sfdt-color-*)` CSS custom property. The raw values live in one place — `lib/tokens.ts` — which each surface injects at boot (`ensureTokens()` on Salesforce pages; the `:root` token block prepended to the app/options stylesheets). This is a pure refactor with no user-facing change; it's the enabling step for a future single-switch dark theme, which can now supply dark values in one file instead of hunting colours across the codebase. One documented exception remains: the user-configurable `canvasSearch.highlightColour` default (`#FFD700`) stays a literal because it's runtime data string-concatenated with an alpha suffix and cannot be a CSS variable.
