# Versioning and the public surface

**Status:** adopted 2026-08-22, opening the "Trustworthy writes" phase.

`CHANGELOG.md` has always said this project adheres to Semantic Versioning. That sentence is
not enough on its own: semver is a promise about a *named* surface, and until now sfdt never
said which surface it was promising about. This file says it, so that 1.0 means something
other than "the version number went up".

The wire protocol already had a real policy ([RELEASING.md](../RELEASING.md) — "Wire-protocol
version") and `@sfdt/flow-core` already had a per-package rule. Neither changes here; this
file covers the surfaces they don't.

## What is public

The public surface of `@sfdt/cli` is exactly what the generated catalogs describe. They are
regenerated by `npm run generate:catalogs` and drift-checked in CI, so this list cannot
silently disagree with what ships:

| Surface | Catalog | Contract |
|---|---|---|
| CLI commands, subcommands and flags | `generated/commands.json` | argv shape and exit codes |
| The `--json` envelope | `generated/commands.json` (`supportsJson`) | stdout only; on-disk snapshots stay raw (principle #6) |
| MCP tools, their inputs and `confirmExecution` gating | `generated/mcp-tools.json` | tool names and schemas |
| Config keys | `src/lib/config-schema.json` | key names, types, defaults |
| Bridge request kinds | `generated/bridge-contract.json` | governed by `PROTOCOL_VERSION`, see RELEASING.md |
| GitHub Action inputs | `action.yml` | input names and semantics |
| `@sfdt/flow-core` exports | `packages/flow-core/src/index.ts` | governed by its own per-package rule |

**Not public**, and free to change in any release: everything under `src/lib/` as a module
(sfdt is a CLI, not a library — import paths are internal), GUI routes and page markup,
VS Code command ids, Chrome feature ids, the shape of files under `logs/`, and the
`.harness/` telemetry format.

## What a version bump means

- **MAJOR** — a public surface is removed or changes meaning: a command or flag deleted or
  renamed, an exit code repurposed, a `--json` field removed or retyped, an MCP tool removed
  or its input schema narrowed, a config key removed, an Action input removed.
- **MINOR** — additive: a new command, flag, MCP tool, config key or `--json` field. Adding a
  field to the envelope is minor because consumers must tolerate unknown fields.
- **PATCH** — behaviour fixes that no correct consumer was relying on.

Two carve-outs, stated so they are choices rather than accidents:

- **Beta-dependent surfaces.** Where sfdt depends on a Salesforce beta API
  (`deployment.smart.useRelevantTests`, `sfdt test --logic`, elastic async Apex in
  `monitor limits`), the *sfdt* surface follows the rules above, but the underlying behaviour
  can change or vanish when Salesforce changes it. These are marked **Shipped (beta)** in
  `ROADMAP.md` and are excluded from the MAJOR guarantee. A beta surface graduating to stable
  is a MINOR.
- **Gated org checks.** A check that degrades to `warn`/`skipped` without a license or edition
  is behaving correctly, not breaking. Changing *which* degradation applies is a PATCH.

## Deprecation runway

A public surface is never removed without first being deprecated:

1. Mark it deprecated in its own description and in `CHANGELOG.md`, naming the replacement.
2. Keep it working, and warn on use where a warning has somewhere to go (stderr for the CLI,
   never inside the `--json` envelope on stdout).
3. Remove it no earlier than the next MAJOR, and never less than one minor release later.

Currently deprecated, with the runway now started:

| Surface | Replacement | Removal |
|---|---|---|
| `action.yml` input `command` | `args-json` | at 1.0.0 |
| The four legacy settings shapes in `extension/lib/settings.ts` | `registerSettingsShape(...)` | at the next extension MAJOR |
| `bridge-contract.ts`'s pre-1.0 optional field | required on all servers | at protocol 2.0, which per RELEASING.md cannot ship before the matching extension clears Web Store review |

## What 1.0 requires

1.0 is not a feature milestone — the surface is already broad. It is the release where the
promises above start binding. To cut it:

- [ ] Every item in the deprecation table marked "at 1.0.0" is removed.
- [ ] `generated/summary.json` is the declared frozen surface, and the release notes quote it.
- [ ] No public surface depends on an experimental Node API. Today `run-history.js` and
      `pull-cache.js` use `node:sqlite`, which is experimental in Node 22 and prints a warning
      to users — either it is stable in the supported Node floor, or the warning is suppressed
      and the dependency documented as internal (it is: `logs/history.db` is not public).
- [ ] The two known flaky tests (`test/lib/bridge-routes-extra.test.js`,
      `test/lib/gui-server-routes3.test.js`) are fixed, so `npm test` can return to
      `prepublishOnly` — see RELEASING.md.
- [ ] `SECURITY.md`'s supported-version table names the 1.0 line.

## Support window

The latest minor line receives security fixes. Older lines do not. At 1.0 this becomes: the
current MAJOR receives security fixes; the previous MAJOR receives them for six months after
its successor ships.
